## 1. Executive Summary

**The migration is technically small and commercially/operationally large.**

Only **three files** in the whole workspace actually talk to PayMongo. Everything else that
mentions the name is a comment, a type doc, or one line of customer-facing copy. The
integration uses the narrowest possible slice of PayMongo: hosted Checkout Session creation,
one webhook event, and a boolean. There is **no refund call, no tokenization, no saved cards,
no recurring billing, no payment-intent/attach flow, and no client-side SDK**. That is the
single biggest fact in this report — it makes the code migration a days-scale job.

What is *not* days-scale:

1. **Maya has no merchant self-serve path to production.** Going live requires a Maya
   Relationship Manager, Maya-side acceptance testing (UAT), a formal sign-off, a coordinated
   go-live date, and production credentials *issued by Maya* rather than generated by us.
   Maya's own published journey adds up to roughly **4–8 weeks** end to end. **[MD]**
   This is the launch blocker, not the code.
2. **Maya webhooks are not signed.** There is no HMAC, no signature header, no shared signing
   secret — authenticity is expected to come from **IP allowlisting** of four documented Maya
   egress IPs. **[MD]** Our current webhook's entire trust model is the HMAC at
   `booker/app/api/payment/webhook/route.ts:5-34`. That model does not port; it must be
   *replaced*, not translated. This is B2 and it is the most important engineering item here.
3. **Maya's sandbox cannot test most of the payment methods we currently accept.** Maya
   states plainly that *"Maya is the only e-wallet available for testing in Sandbox. Other
   e-wallets like GCash, QRPh, ShopeePay, and WeChat can only be tested in the Production
   environment."* **[MD]** Our current live set is card, GCash, GrabPay, Maya, BillEase, QR Ph.
4. **Payment-method parity is probably lost.** Maya Checkout documents cards, digital wallets
   + QR Ph, and Apple Pay, each of which **must be enabled per-merchant by Maya**. **[MD]**
   GCash and ShopeePay are named as supported wallets; **GrabPay and BillEase are not named
   anywhere in Maya Checkout's documentation.** **[C]** Losing BNPL (BillEase) and GrabPay is
   a product decision, not an engineering one.

**Recommendation (technical):** if the migration proceeds, use **Maya Checkout** (hosted,
redirect-based, `POST /checkout/v1/checkouts`) — it is a near-exact structural match for our
PayMongo Checkout Session usage, keeps us out of PCI scope, and requires no browser SDK, so
`next.config.ts`'s CSP stays untouched. Do **not** use Pay with Maya (Maya-wallet-only, drops
card acceptance) or Maya Vault (card tokenization — we have no saved-cards feature to justify
the PCI surface).

**Recommendation (commercial):** this decision should be made on fees, settlement terms and
merchant support, not on technology. Note the point already recorded in
`architecture/booking-flow.md`: **`"paymaya"` is already in our `payment_method_types`, so
customers can already pay with Maya today** — PayMongo is merely the acquirer. A customer
sees almost no change. The upside must come from the commercial terms.

**Verdict:** feasible, low code risk, high process risk. Do not commit to a launch date that
depends on Maya production credentials until a Relationship Manager has confirmed one.

## 2. Current PayMongo Architecture

### The flow, end to end (booker)

```
Browser (booking wizard, step 6)
  └─ createBooking()                            services/bookings.service.ts:29-48
       └─ INSERT bookings (price_paid DERIVED BY DB TRIGGER, never sent)
  └─ POST /api/payment/create-session {bookingId}   useBookingWizard.ts:197-201
       ├─ authenticate caller (SSR cookie client)    route.ts:31-33
       ├─ read PAYMONGO_SECRET_KEY                   route.ts:35-36
       ├─ service-role read of booking, assert booker_id === user.id   route.ts:45-52
       ├─ amountCentavos = round(price_paid * 100)   route.ts:55
       ├─ resolveSiteUrl().origin  (throws, never guesses)  route.ts:79-90
       ├─ POST https://api.paymongo.com/v1/checkout_sessions   route.ts:93-108
       └─ UPDATE bookings SET payment_reference = data.id      route.ts:120
  └─ window.location.href = checkout_url        useBookingWizard.ts:216   ← leaves the app

PayMongo hosted checkout → customer pays

  ├─ redirect → /?payment=success|cancel&booking_id=<uuid>
  │    └─ useAppShell.ts:132-151 — toast only; RLS-verifies the id belongs to this user
  │       before claiming success. NEVER writes is_paid.
  │
  └─ webhook (authoritative) → POST /api/payment/webhook
       ├─ HMAC-SHA256 over `${t}.${rawBody}`, header `paymongo-signature`  route.ts:5-34
       ├─ read event.data.attributes.type   ← NOT data.type (see below)   route.ts:62-75
       ├─ bookingId = ...attributes.data.attributes.metadata.booking_id   route.ts:73
       ├─ UPDATE bookings SET is_paid=true WHERE id=? AND is_paid=false   route.ts:99-104
       │     └─ DB trigger bookings_create_transaction fires false→true
       │        → booking_transactions ledger row (20260725000002:149-151)
       └─ best-effort `payment_confirmed` notification to vendor admins  route.ts:151-187
```

### The kiosk fork (vendor)

`vendor/app/api/kiosk/payment/create-session/route.ts` is a **deliberate fork**, documented as
such at its head. It is byte-for-byte the same session construction; the only difference is the
ownership rule — the caller must be a **vendor-admin of `booking.vendor_id`** (`requireVendorAdmin`,
`route.ts:50-51`), plus two extra guards: the booking must belong to the named vendor
(`route.ts:68-70`) and must be `booked_via === "kiosk"` (`route.ts:74-76`). Return URLs point at
`/kiosk` rather than `/`. Driven from `useKioskCheckout.ts:67-101`.

**There is exactly one webhook, on booker, and it settles kiosk payments too.** It keys purely
on `metadata.booking_id` and writes with service role — no app-scoping, no booker-scoping. This
is a designed invariant, recorded at `vendor/app/api/kiosk/payment/create-session/route.ts:18-23`
and in `architecture/booking-flow.md`, and it is why `PAYMONGO_WEBHOOK_SECRET` is **booker-only**.

### State model

| Concept | Where it lives | Notes |
|---|---|---|
| Payment happened | `bookings.is_paid boolean not null default false` | `20260518000001` |
| Provider's id | `bookings.payment_reference text` | stores the **Checkout Session id** (`cs_…`) |
| Money ledger | `booking_transactions` | written **only** by trigger on `is_paid` false→true |
| Payout lifecycle | `booking_transactions.payout_status` | `held → releasable → released`, or `reversed` |
| Booking lifecycle | `bookings.status` (9 states incl. `refunded`) | **entirely separate from payment** |

**`is_paid` is a one-way boolean.** There is no `payment_status` enum, no `failed`, no
`expired`, no `refunded` payment state. A failed/abandoned/expired payment is represented by
the *absence* of a transition — `is_paid` stays false and no ledger row is ever created
(`20260725000002:16-21`).

### Success / failure / cancel / refund / retry behaviour today

- **Success:** webhook sets `is_paid`. Redirect only shows a toast.
- **Failure:** PayMongo has no separate failure URL in our config — a failed card keeps the
  customer on PayMongo's page. We learn nothing.
- **Cancel:** `cancel_url` → toast *"Payment cancelled. Your booking is saved as pending."*
  The booking row **stays** as `pending`, unpaid, holding a capacity slot.
- **Refund:** **the PayMongo refund API is never called.** `schema.md:884` says so explicitly:
  *"there is no refund mechanism in this system"*. `bookings.status = 'refunded'` and
  `payout_status = 'reversed'` are bookkeeping-only, set by humans, and the schema doc warns
  never to label `reversed` as "Refunded" in UI.
- **Retry:** there is no retry path. A booker who abandons checkout has an unpaid `pending`
  booking; re-running the wizard creates a *new* booking (or hits the
  `UNIQUE (booker_id, schedule_id, booked_date)` constraint → `"already_booked"`). At the
  kiosk a failed session leaves *"The booking was created but payment could not start. Please
  see staff."* (`useKioskCheckout.ts:97`).
- **Unpaid-but-fulfilled** is an accepted state: `useBookingRow.ts:71` and
  `ezzy-vendor-mobile/.../useBookingActionBar.ts:86-97` **warn but never block** a vendor
  fulfilling an unpaid booking, because there is no "collect payment" action to escape to.

### Environments today

Test and live are separated purely by **which PayMongo key each deployment holds**
(`sk_test_` vs `sk_live_`) and **which webhook registration exists in that mode**. There is no
`PAYMENT_PROVIDER` or `*_ENVIRONMENT` variable anywhere — the key *is* the environment
selector, and the API host is a hardcoded literal in both routes. `architecture/overview.md:140-162`
records three invisible failure modes already hit in production: wrong mode, two different
PayMongo accounts across booker/vendor, and a stale registration.

**Session lifetime:** *"Checkout sessions are valid for 1 hour. If expired, generate a new
checkout request."* **[MD]**

**Payment statuses** **[MD]** — transient: `PENDING_TOKEN`, `PENDING_PAYMENT`,
`FOR_AUTHENTICATION`, `AUTHENTICATING`, `AUTH_SUCCESS`, `PAYMENT_PROCESSING`. Semi-final:
`PAYMENT_SUCCESS`, `AUTHORIZED`, `CAPTURED`. Final: `AUTH_FAILED`, `DONE`, `PAYMENT_FAILED`,
`PAYMENT_EXPIRED`, `PAYMENT_CANCELLED`, `VOIDED`, `REFUNDED`, `CAPTURE_HOLD_EXPIRED`.
Maya's rule: *"Always wait for webhook events before updating your order system. Do not rely
solely on synchronous responses."* **[MD]** — which is exactly our existing discipline.

**Webhooks** **[MD]**
- Register: `POST /payments/v1/webhooks` with `{name, callbackUrl}`, secret key.
- Current event names: `PAYMENT_SUCCESS`, `PAYMENT_FAILED`, `PAYMENT_EXPIRED`,
  `PAYMENT_CANCELLED`, `AUTHORIZED`, `3DS_PAYMENT_*`, `RECURRING_PAYMENT_*`.
- Legacy `CHECKOUT_SUCCESS`/`CHECKOUT_FAILURE`/`CHECKOUT_DROPOUT`/`CHECKOUT_CANCELLED` still
  accepted but Maya says to *"Subscribe to the corresponding PAYMENT_* events as soon as
  possible."* → **use `PAYMENT_*`.**
- Payload = *"the successful response of the GET Payment endpoint"* — so it carries `id`,
  `status`/`paymentStatus`, `amount`, `currency`, `requestReferenceNumber`, `fundSource`,
  `receiptNumber`.
- **Retries: 4 attempts total — immediate, +5 min, +15 min, +45 min.** Then it stops.
- **Environment-specific:** *"Webhooks are environment specific. They must be registered again
  on Production."*
- **Source IPs** — sandbox `13.229.160.234`, `3.1.199.75`; production `18.138.50.235`,
  `3.1.207.200`. Maya: *"strongly recommended to configure your network to accept webhook
  traffic only from the IPs listed above."*
- **No signature. No HMAC. No signing secret.** Not in the docs, not in Maya's own webhook
  demo repo (which *"simply logs any incoming request"*) **[MD][MX]**.

**Voids & refunds** **[MD]** — void same day before 23:59 GMT+8; refund from 00:00 the next
day, within **180 days**; **partial refunds supported**. Error codes `PY0072` (refund before
cut-off) and `PY0073` (void after cut-off) enforce the boundary. Exact endpoints were not
retrievable from the public pages I fetched — **[?]** to confirm with Maya. Irrelevant to
parity (we call no refund API today) but relevant to §15's opportunity list.

**Rate limits & idempotency** **[MD]/[3P]** — Maya rate-limits and returns **HTTP 429**;
guidance is exponential back-off. Maya advises *"unique value for this property for each
transaction"* for `requestReferenceNumber` but **does not enforce it** — `GET
/payments/v1/payment-rrns/{rrn}` returns an **array**, so one RRN can legitimately map to
several payments. There is **no `Idempotency-Key` header** documented for Checkout. See D1.

**Error codes** **[MD]** — `PY0009` payment does not exist (404), `PY0044` payment invalid (400),
`PY0047` ineligible for refund (401), `PY0057` payment expired (422), `PY0100` authentication
failed, `PY0101` acquirer decline (high risk), `PY0120` issuer decline, and others.

**SDKs** **[MX]** — `PayMaya/PayMaya-Node-SDK` (npm `paymaya-node-sdk`), PHP/Ruby/iOS/Android
SDKs, and demo repos `maya-demo-checkout-ts`, `maya-demo-webhooks-ts`. All are thin, low-star,
minimally-maintained wrappers around two `fetch` calls. **[C] Do not add a dependency** — our
current integration is a `fetch`, and staying dependency-free avoids an approval gate and a
supply-chain surface for no benefit.

## 5. Recommended Maya Integration Approach

**Use Maya Checkout, server-side only, redirect-based, webhook-authoritative.** Keep the
existing architecture *exactly*; replace only the three provider-coupled files.

Why this and not something that "looks more modern":

- **It preserves the property that matters most:** we never touch card data, so PCI scope
  stays at SAQ-A. Maya Vault or the direct Payments API would move us to SAQ-D for a feature
  (saved cards) nobody has asked for. Simplicity-first, per AGENTS.md.
- **It preserves the CSP posture.** No browser SDK → `api.paymongo.com`'s deliberate absence
  from `booker/next.config.ts:102-109` becomes `pg.maya.ph`'s deliberate absence. Top-level
  navigation is governed by neither `connect-src` nor `form-action`. **No CSP change at all.**
- **It preserves the single-webhook design.** Maya emits webhook events on the **merchant
  account**, registered per environment — not per app — so one endpoint on booker still settles
  both booker and kiosk payments. `vendor` still holds no webhook secret (and now, no webhook
  anything).
- **It preserves the ledger.** `booking_transactions` fires on the `is_paid` column. Untouched.
- **It requires no migration.** `payment_reference` is `text`.

**What must change in kind, not just in name:** the webhook's trust model (B2), the amount
unit (B3), and the booking↔payment correlation key (B1).

HTTP call on a rare path and it makes B2's absence of an HMAC survivable. **[C]**

**Design notes**
- **`MAYA_ENVIRONMENT` is not decoration.** PayMongo encoded the environment in the *key prefix*
  and used one host, so the host could be a literal. Maya uses **different hosts**, so an
  explicit selector is required. Deriving it from the key prefix is not possible (`pk-`/`sk-`
  carry no environment marker) — **[C]** and this is the single most likely new
  misconfiguration. Make the route **fail loudly** on an unrecognised value; never default to
  production, and never default to sandbox either.
- **`MAYA_PUBLIC_KEY` is never `NEXT_PUBLIC_`.** Maya calls it "public" because it is safe *in a
  browser SDK context*; ours is not that. It mints checkout sessions against our merchant
  account, and nothing in our design needs it client-side. Prefixing it would be a real
  regression against `AGENTS.md`'s secret rules. **[C]**
- **`MAYA_SECRET_KEY` on vendor: open.** The kiosk route only *creates* checkouts (public key).
  It needs the secret key only if we ever verify from vendor. Recommendation: **do not add it**
  — same reasoning that keeps `PAYMONGO_WEBHOOK_SECRET` off vendor (kiosk plan B22): an unused
  credential in a second environment is a credential with no purpose. → D2.
- **Both apps must use the same Maya merchant account and the same environment**, exactly as
  `production-env-checklist.md:61-68` already requires for PayMongo. The failure is invisible.
- **Storage:** Vercel project environment variables per environment (staging project vs
  production project), marked as Secret. Never in `.env.local` committed anywhere; never in

## 12. Webhook Strategy

**Keep exactly one webhook endpoint, on booker.** It settles booker and kiosk payments alike,
because Maya emits on the merchant account and our handler keys on the booking reference with
service-role writes. This is the same invariant as today
(`vendor/.../create-session/route.ts:18-23`) and Maya's model does not disturb it. **[C]**

**Subscribe to four events**, act on one at first:

| Event | Initial behaviour |
|---|---|
| `PAYMENT_SUCCESS` | verify, then `is_paid = true` (the only money-affecting write) |
| `PAYMENT_FAILED` | log only (phase 1) → later, surface truthfully to the booker |
| `PAYMENT_EXPIRED` | log only → later, release the held capacity slot |
| `PAYMENT_CANCELLED` | log only |

Shipping the last three as **log-only** keeps the migration a like-for-like swap while
capturing the data needed to justify acting on them later. **[C]**

**Trust model — the replacement for the HMAC (B2). Decided: D3 option (c), 2026-09-07.**
Three layers, applied in this order. Layers 1–2 are cheap filters that keep unauthenticated
traffic away from layer 3; **layer 3 is the one the security of the endpoint actually rests
on** and may not be dropped for latency, convenience, or because the first two "should be
enough":
1. **Unguessable path.** `/api/payment/webhook/<MAYA_WEBHOOK_PATH_TOKEN>` (or a header token
   Maya echoes — **[?]** Maya's docs do not document custom webhook headers, so a path segment
   is the reliable option). Anything else → 404.
2. **Source-IP allowlist.** Sandbox `13.229.160.234`, `3.1.199.75`; production
   `18.138.50.235`, `3.1.207.200` **[MD]**. Selected by `MAYA_ENVIRONMENT`; mismatch → 403 + log.
3. **Re-fetch before believing anything — the load-bearing layer.**
   `GET /payments/v1/payments/{id}` with the **secret** key; require
   `status === "PAYMENT_SUCCESS"` **and** an `amount` equal to the booking's `price_paid`
   before any write. The POST body is treated as a *hint that something happened*, never as
   evidence. **[C]** Maya's docs independently suggest the same endpoints as a fallback for
   webhook-processing failures **[MD]**.
   - Take the payment id from the **body**, but everything decided afterwards comes from the
     **response**. Never trust a `status` or `amount` that arrived in the POST.
   - A `404` / `PY0009` ("payment does not exist") means the id was invented → **403 + log**,
     never a silent 200.
   - An amount mismatch is a **permanent** fault, not a transient one: log loudly, do not
     write, do not ask Maya to retry (I1).
   - This costs one outbound HTTP call on a rare path. That is the entire price of not having
     a signature, and it is worth paying.
4. **Idempotent write.** `WHERE is_paid = false`, unchanged — and now mandatory, because Maya
   delivers up to 4 times.
5. **Never echo the reason in the response body** — the endpoint is public. Keep the current
   discipline (`webhook/route.ts:106-123`): `code` and `message` to the log, never `details`.

**Response codes — a deliberate change from today (I1).** Today the route answers `200` even
when the `is_paid` write fails, because PayMongo would retry and *"a retry cannot fix a bad key
or a wrong environment"*. Maya gives us **exactly four attempts over 45 minutes** **[MD]** —
a much scarcer resource, and one that maps well onto *transient* failures. Proposal:
- `200` — settled, or a benign replay, or an event we deliberately ignore.
- **`500` — transient failure only** (Supabase unreachable, Maya read timed out). Let Maya
  retry; four attempts across 45 minutes is a genuine safety net our current design forgoes.
- `200` + `console.error` — permanent faults (unknown booking id, amount mismatch). Retrying
  cannot help, and 45 minutes of noise is worse than one loud log line.

**Response *time* is a new constraint, and D3 settles how it is spent.** Maya asks for a 200
*"within 5 seconds"* **[MD]**; PayMongo published no budget. The re-fetch and the
`payment_confirmed` fan-out cannot both sit in front of the response, so:
**the re-fetch stays (it is the security gate) and the fan-out moves behind the response.**
Fixed handler order:

```
IP allowlist  →  path token  →  GET /payments/v1/payments/{id}  →  assert status + amount
   →  idempotent is_paid write  →  RETURN 200  →  payment_confirmed fan-out (after the response,
                                                  or from a DB trigger — see I7)
```

Everything up to and including `RETURN 200` must fit the 5s budget on a **cold start**. See **I7**.

**Registration discipline** (carried over from `booking-flow.md`, still true):
- Deploy first, register second.
- Test and production are separate registrations with separate keys.
- An unsigned/unauthenticated POST returning `404`/`403` is the endpoint **working**.
- **Verify only by the database:** `select is_paid from bookings where id = '<uuid>'`. A `200`
  proves delivery, never settlement — the lesson from the `data.type` incident.

## 13. Testing Strategy

**Start by closing the gap this research exposed:** there are currently **zero** automated tests
around payments, and both historical production incidents were unit-testable. Do not port the
integration without porting this gap closed. → I3.

**Unit (machine-verifiable, no network):**
1. **Amount mapping** — `price_paid = 1234.50` → `totalAmount.value === 1234.5`, **not**
   `123450`. Guards B3, the highest-consequence single line in the migration.
2. **RRN encode/decode round-trip** — booking uuid → RRN (**35 chars, asserted ≤36**) → booking
   uuid; plus the reject cases (short, non-hex, empty) and the `payment_reference` fallback.
   Two different suffixes must decode to the **same** booking. Guards B1.
3. **Webhook payload parsing** — a captured `PAYMENT_SUCCESS` body yields the right booking id;
   an unrecognised shape yields `null` and logs. Guards the successor to the `data.type` trap.
4. **IP allowlist** — allowed IP passes, `X-Forwarded-For` spoof attempts and unknown IPs 403.

## 14. Security Considerations

| Area | Maya's position | Ours |
|---|---|---|
| **Webhook authenticity** | **No signature.** IP allowlist recommended. **[MD][MX]** | ⚠️ **The single biggest regression.** Mitigate with path token + IP allowlist + **server-side re-fetch** (§12). Never write `is_paid` from an unverified body |
| Public vs secret key | `pk-` creates checkouts; `sk-` reads payments and manages webhooks **[MD]** | **Both stay server-only.** `pk-` is not `NEXT_PUBLIC_`. Rotate via Business Manager (delete + regenerate) if leaked **[MD]** |
| Server- vs client-side calls | Maya's own demo warns to call from the backend **[MX]** | Already true and must stay true. Nothing about Maya belongs in a bundle |
| HTTPS | Hosted page and API are HTTPS; `callbackUrl` must be publicly reachable HTTPS | Unchanged |
| **Idempotency** | No `Idempotency-Key` for Checkout; RRN "advised" unique but not enforced; RRN lookup returns an **array** **[MD]** | Our `WHERE is_paid = false` guard is the real idempotency and it is unchanged. **Do not** rely on Maya to de-duplicate |
| **Replay protection** | Nothing — no timestamp, no nonce, no signature **[C]** | The `is_paid = false` guard plus the amount+status re-fetch make a replayed body a no-op. A replayed *stale* body cannot flip a booking twice |
| Rate limits | HTTP 429; exponential back-off **[MD]** | New: handle 429 on create-session as a user-visible "please try again", not a 502 |
| Logging | — | Keep today's rule: `code`/`message` only, never `details`, never row content. **Never log `pk-`/`sk-` or a full webhook body containing `fundSource` card details** |
| Card / customer data | Hosted page — we never see a PAN | Unchanged. **Do not send `buyer.billingAddress`/`shippingAddress`** — we hold no such data and sending PII we don't need is gratuitous. Send at most a name/email, and only if Maya requires it |
| **PCI** | Hosted redirect keeps us at **SAQ-A**; Maya runs *"periodic PCI-DSS compliance reviews"* via the RM **[MD]** | Choosing Maya Vault or the direct Payments API would push us to SAQ-D. **Don't** |
| Secrets management | Keys shown **once** on generation **[MD]** | Vercel env vars per environment, marked secret. Capture at generation time |

### Places our current PayMongo architecture must **not** be reproduced verbatim

1. **`webhook/route.ts:36-45` — "verify the signature, then trust the body."** There is no
   signature to verify. Copying the structure and simply deleting the check would leave a
   **public, unauthenticated endpoint that sets `is_paid` from attacker-controlled JSON**. This
   is the one place where a mechanical port is actively dangerous. → B2.
2. **`webhook/route.ts:124-129` — always answer 200.** Correct under PayMongo's retry policy;
   wasteful under Maya's four-attempt budget. → I1.
3. **`route.ts:55` — `Math.round(price * 100)`.** Correct for PayMongo, **charges 100× on Maya**.
   → B3.
4. **`metadata.booking_id`.** Maya's `metadata` is a payment-facilitator structure, not a
   free-form bag. Assuming it round-trips is the exact class of error that caused the
   `data.type` incident. → B1.
5. **Everything else about the current design should be reproduced deliberately**, in particular:
   authenticate **before** the config check (booker B1 / vendor B20); derive the amount from the
   DB row, never the client; `resolveSiteUrl()` throws rather than guessing; the redirect never
   writes `is_paid`.

## BLOCKERS

### B1 — The booking↔payment correlation key must be redesigned  ⬜ TODO
**Files:** `booker/app/api/payment/create-session/route.ts:104`,
`vendor/app/api/kiosk/payment/create-session/route.ts:135`,
`booker/app/api/payment/webhook/route.ts:62-73`
PayMongo's `metadata.booking_id` is *"the entire contract"* — the only link from a payment back
to a row. Maya's `metadata` is **not** a general-purpose bag (it is
`subMerchantRequestReferenceNumber` + `pf.*` for payment facilitators) **[MD]**, so the
correlation must move to **`requestReferenceNumber`** — which is capped at **36 characters**.
A UUID is **exactly 36**, leaving **zero room** for a retry/attempt discriminator, while Maya
advises a unique RRN per transaction.
**Fix approach — D1 resolved 2026-09-07, option (a).** Exact shape:

```
requestReferenceNumber = <32 hex chars: booking uuid, dashes stripped> "-" <2 chars base36>
                         e.g.  a1b2c3d4e5f60718293a4b5c6d7e8f90-k7          (35 chars, cap 36)
```

- **Encode** in both create-session routes, immediately before the Maya call. The suffix is
  random (36² = 1296) rather than a counted attempt number, so it needs **no extra query and no
  new column**; a repeat within one booking is harmless, since Maya permits duplicate RRNs
  (`GET /payments/v1/payment-rrns/{rrn}` returns an **array** by design **[MD]**).
- **Decode** in the webhook: `slice(0, 32)` → re-insert dashes → validate it is a well-formed
  uuid → look the booking up. Reject anything that is not 32 hex characters rather than
  attempting a partial match.
- **⚠️ Read the RRN from the D3 re-fetch response, never from the POST body.** The body is a
  hint; `GET /payments/v1/payments/{id}` is the evidence, and it carries
  `requestReferenceNumber` **[MD]**. This is what keeps B1 and B2 from contradicting each other.
- **Fallback:** if the RRN is missing or unparseable, resolve via
  `bookings.payment_reference = <payment id>`. If **both** fail, this is a *permanent* fault —
  log loudly with the id, return 200, do not invite a retry (I1).
- **Nothing is stored for this.** No column, no migration, no approval gate.

Round-trip unit test is mandatory (§13 test 2).

### B2 — Maya webhooks are unsigned; the current trust model does not port  ⬜ TODO
**File:** `booker/app/api/payment/webhook/route.ts:1-45` (the entire `verifySignature` design)
Our webhook's whole authenticity story is an HMAC-SHA256 with a constant-time compare. **Maya
provides no signature, no signing secret and no timestamp** — its guidance is IP allowlisting,
and its own webhook demo *"simply logs any incoming request"* **[MD][MX]**. Deleting the
signature check and keeping the structure would leave a **public, unauthenticated endpoint that
writes `is_paid` from attacker-supplied JSON** — i.e. anyone who learns the URL and a booking id
could mark bookings paid and mint `booking_transactions` rows.
**Fix approach:** three layers, none sufficient alone — unguessable path token; source-IP
allowlist keyed off `MAYA_ENVIRONMENT`; and, decisively, **re-fetch
`GET /payments/v1/payments/{id}` with the secret key and require `PAYMENT_SUCCESS` *and* a
matching amount before any write**. Treat the POST body as a hint, never as evidence.
**→ D3 resolved 2026-09-07: this is the chosen approach.** The re-fetch is the load-bearing
layer and is not optional — the path token and IP allowlist are the outer layers around it, and
neither may be traded for it. Ordering inside the handler is fixed by I7.

### B3 — Amount units change from centavos to major units  ⬜ TODO
**Files:** `booker/app/api/payment/create-session/route.ts:55,99`,
`vendor/app/api/kiosk/payment/create-session/route.ts:80,126`
PayMongo takes an integer of centavos; Maya's `totalAmount.value` is a **decimal in major
units, 0.01–9999999** **[MD]**. Porting `Math.round(Number(price_paid) * 100)` unchanged would

**Fix approach:** send `Number(booking.price_paid)` at 2 dp; keep the `> 0` guard; keep deriving

### I1 — The always-200 webhook response is wrong for Maya's retry budget  ⬜ TODO
**File:** `booker/app/api/payment/webhook/route.ts:124-129, 148`
Answering `200` even when the `is_paid` write fails is deliberate and correct **for PayMongo**.
Maya retries **exactly four times — immediately, +5 min, +15 min, +45 min — then stops** **[MD]**.
That is a scarce, valuable resource for *transient* failures, and we currently throw it away.
**Fix approach:** `200` for settled / benign replay / deliberately-ignored; **`500` only for
transient failures** (Supabase unreachable, Maya read timeout); `200` + `console.error` for
permanent faults where a retry cannot help. Never put the reason in the body.

### I2 — `MAYA_ENVIRONMENT` is a new, invisible misconfiguration surface  ⬜ TODO
**Files:** both create-session routes, the webhook route

a bad key**. This repo has already been burned three times by invisible environment crossover
(`overview.md:150-162`).
**Fix approach:** one resolver, used by all three routes; **throw on any unrecognised value**;
never default in either direction; log the resolved host (not the key) once at first use.

A PayMongo Checkout Session created shortly before cut-over can still be paid afterwards. If the

**charged with `is_paid` left false and no ledger row** — the exact silent failure this codebase
has fought twice.
**Fix approach:** keep the PayMongo webhook registered and its handler deployed for a defined
tail (≥24h), decommission in phase 12 only, and query for `is_paid = false` bookings with a
`cs_`-prefixed `payment_reference` before unregistering.

### I7 — Maya wants a 200 within ~5 seconds; our handler does a notification fan-out first  ⬜ TODO
**File:** `booker/app/api/payment/webhook/route.ts:151-187`
Maya's guidance is explicit: *"Your webhook endpoint should always return a 200 OK response as
quickly as possible (within 5 seconds) or before executing complex logic or validations"* **[MD]**.
PayMongo published no such budget, so the current handler settles `is_paid` and then, **inline
and before responding**, runs a `payment_confirmed` fan-out: two queries, then three more, then a
`vendor_members` read, then an insert — six sequential round trips on a route that may also be
cold-starting. Under Maya that risks a timeout Maya reads as a failed delivery, burning one of
only four attempts and re-delivering an event we already settled.
**⚠️ This pulls against B2, and D3 has decided which side wins.** The re-fetch that makes the
unsigned webhook safe (`GET /payments/v1/payments/{id}`) *adds* latency to the same budget, and
both cannot sit in front of the response. **The re-fetch stays in front; the fan-out moves
behind.** Security is not traded for latency here — if the budget is tight, the fan-out is what
gives way, never the verification.
**Fix approach:** settle first, respond immediately, do the notification work after. Order:
IP + path check → re-fetch verification → idempotent `is_paid` write → **return 200** →
notification fan-out. Keep the fan-out's existing "failure must never affect the response"
property.
**⚠️ Corrected by I8 (2026-09-07):** this originally offered a DB trigger as the fallback. That
was wrong — a trigger is a migration and an approval gate, and it would break this plan's
"no schema change at all" property. Use **`after()` from `next/server`** instead; see **I8**.
**Verify:** measure the handler's end-to-end duration on a sandbox delivery; it must clear 5s
with margin on a cold start, not just a warm one.

### I8 — Post-response work needs `after()`; the DB-trigger option in I7 was wrong  ⬜ TODO
**Files:** `booker/app/api/payment/webhook/route.ts:151-187`, `booker/package.json:37` (Next 16.2.4)
**Found by the 2026-09-07 review pass — this corrects I7.** I7 said to "settle, respond, then run
the fan-out", and offered a DB trigger as the alternative. Both halves needed correcting:
- **"Respond then work" is not free on serverless.** Work started but not awaited before the
  handler returns is not guaranteed to run — the function can be frozen or torn down. Written
  naively, the `payment_confirmed` notification would silently stop being sent, and nothing
  would report it. That is the exact failure shape this codebase keeps getting bitten by.
- **The DB-trigger alternative contradicted this plan's own best property.** A trigger is a
  migration, which is an approval gate, and it would break the "**no schema change at all**"
  claim in D1 and §16. It should never have been offered as a casual fallback.
**Fix approach:** use **`after()` from `next/server`** — stable since Next 15.1, and both apps
are on **Next 16.2.4**, so **no new dependency and no approval gate**. Settle `is_paid`, return
200, and run the notification fan-out inside `after()`. Keep its existing "failure must never
affect the response" property; `after()` runs within the route's max duration, so the fan-out
must still be bounded, not unbounded.
**Verify:** a sandbox `PAYMENT_SUCCESS` returns 200 inside the 5s budget **and** the
`payment_confirmed` notification rows still appear. Both, not either — the whole risk here is
that the response looks fine while the deferred half quietly stops running.

### I11 — Nothing would tell us the new webhook stopped settling  ⬜ TODO
**Files:** none yet — that is the gap
**Found by the 2026-09-07 review pass.** This repo has been bitten **three times** by payment
failures that were invisible: the `data.type` envelope bug (green delivery logs, months), the
missing `PAYMONGO_SECRET_KEY` on staging-vendor, and the crossed-over deployments in

incidents on day one.

> **Status (2026-09-07): D1–D9 resolved. D0 is the only one still open, and it is deliberately

- **OPEN — D0 (gates everything): do we migrate at all?** I am **not** resolving this one, and
  the reason is not caution — it is that the inputs that decide it are commercial and neither of
  us has them yet. Recording a "recommendation" here would mean inventing numbers.
  **My technical position, which is an input and not the answer:** there is **no technical
  reason to migrate.** The integration works, and `"paymaya"` is already an accepted payment
  method today — PayMongo is merely the acquirer processing it — so the customer-visible change
  is close to nil. On the technical ledger the swap is mildly *negative*:
  - ✅ ~1 week of engineering; no schema change; the ledger and `payment_reference` are untouched
  - ✅ a real gain in webhook registration by API, and `PAYMENT_*` events we do not have today
  - ⚠️ **a security downgrade** — no signed webhooks, requiring the compensating controls in B2/D3
  - ⚠️ **probable loss of GrabPay and BillEase** (D5), pending the RM
  - ⚠️ **GCash and QR Ph become untestable before production** (§8)
  - ⚠️ **4–8 weeks of Maya-controlled process** with a UAT gate we cannot accelerate (B4)
  **So the commercial case has to carry the whole decision.** What would close this:
  1. Maya's **MDR per channel** vs PayMongo's, in writing — especially cards and GCash.
  2. **Settlement timing** and any holdback/reserve terms.
  3. Contract minimums, monthly fees, or volume commitments.
  4. The A4/U5 answer on GrabPay/BillEase (D5) — a conversion question, not a technical one.
  5. Whether the move is driven by something not in this document (an existing Maya
     relationship, a PayMongo problem, a partnership requirement). If so, say what it is — it
     may change which risks above are acceptable.
  **Until this closes, nothing in this plan executes** — except **I3**, the payment unit tests,
  which are worth writing against the current PayMongo code regardless of the outcome.
- **D1 (B1) — Correlation key → (a) `requestReferenceNumber` = 32-hex booking id + `-` +
  2-char base36 suffix (35 chars), with `payment_reference` as the fallback path**
  (resolved 2026-09-07). Options considered: (a) as chosen; (b) RRN = the raw 36-char UUID;
  (c) rely on `payment_reference = checkoutId` alone.
  **Why not (c):** it fails two ways. The row is written *after* Maya responds, so a fast
  webhook can arrive before the `UPDATE` commits and find nothing — a legitimate payment
  answered with "unknown booking". And a second checkout for the same booking overwrites the
  column, orphaning the first session's event. The RRN has neither problem: it is inside the
  request body, so it exists *before* Maya can call back, and it is immutable per attempt.
  **Why not (b):** a 36-char UUID consumes the entire budget with zero headroom, and Maya
  advises a unique RRN per transaction.
  **Why (a) is not speculative generality:** the decoder is `slice(0, 32)` either way — (b) is
  not *simpler* code, it is the same code with no room left. The only added work is generating
  two characters. Choosing an encoding with headroom over one that sits exactly on a hard limit
  is not adding flexibility for its own sake.
  **Deliberately not stored.** The RRN is self-describing — the booking id is its first 32
  characters — so nothing needs a new column, and the migration keeps its best property: **no
  schema change at all.**
  **Reconciliation note:** the suffix means we cannot look a booking up via
  `GET /payments/v1/payment-rrns/{rrn}` with an exactly re-derived value. We do not use that
  endpoint, `payment_reference` already serves the lookup, and Maya's dashboard still shows the
  booking id in the visible RRN prefix. Accepted.
- **D2 (§11) — `vendor` does NOT get `MAYA_SECRET_KEY`** (resolved 2026-09-07). The kiosk
  route only *creates* checkouts, which is a **public**-key call. Same reasoning as kiosk plan
  B22: an unused credential in a second environment is a credential with no purpose, and its
  presence invites someone to use it.
  **The positive reason, found while resolving this:** the one read vendor might plausibly want
  later — checking a payment's state when the tablet returns (kiosk plan B3, parked) — is
  `GET /payments/v1/payments/{id}/status`, which authenticates with the **public** key **[MD]**.
  So even the obvious future feature does not need the secret key. This is a decision with no
  known expiry, not a deferral.
- **D3 (B2) — Webhook trust model → (c) IP allowlist + secret path + server-side re-fetch
  before writing** (resolved 2026-09-07). Options considered: (a) IP allowlist only, as Maya
  suggests; (b) IP + secret path; (c) all three. **Chosen: (c).** (a) and (b) both make the
  `is_paid` write depend on something forgeable or guessable — a source IP is spoofable and a
  path token leaks the moment it appears in a log, a proxy header or an error report, and
  neither says anything about *the payment*. Only the re-fetch ties the write to a fact Maya
  itself asserts, over a channel authenticated by our **secret** key. Since Maya publishes no
  signature (B2), this is the only layer that is genuinely load-bearing; the other two are the
  cheap outer layers that keep unauthenticated traffic away from it. Maya's own docs point the
  same way, recommending *"fallback APIs, like the `GET /payments` endpoints"* for recovering
  from webhook-processing errors **[MD]**. **Consequence — see I7:** the re-fetch sits in front
  of the response and therefore inside Maya's ~5s budget, so the `payment_confirmed` fan-out
  must move behind the response.
- **D4 (§8) — the sandbox registration points at **staging-booker**; local development uses
  replayed captured payloads, not a tunnel** (resolved 2026-09-07).
  **First, verify A2.** If Maya in fact permits several `callbackUrl`s per event name, register
  a second for a tunnel and this question disappears. The decision below is what we do if A2
  holds and there is only one.
  **Why staging owns it:** staging is shared and always-on; an ngrok URL belongs to one
  developer, dies with their laptop, and takes everyone else's settlement testing with it
  silently — the same class of invisible failure as a stale registration
  (`overview.md:150-162`).
  **Why local development needs no tunnel at all:** the webhook handler's logic — RRN decode,
  status/amount assertion, idempotent write, the ignored-event branch — is exercised by
  **replaying a captured real `PAYMENT_SUCCESS` body** against localhost. That is repeatable,
  costs no shared resource, survives a laptop reboot, and becomes §13 unit test 3. A tunnel
  only buys "a real HTTP call from Maya", which staging already provides.
  **⚠️ The one danger this creates:** replay-against-localhost needs the IP allowlist bypassed
  in development, and that bypass must be impossible to enable in a deployed environment. Gate
  it on `MAYA_ENVIRONMENT === "sandbox"` **and** the absence of `process.env.VERCEL`, and unit-
  test that a production-shaped environment cannot reach the bypass. A dev escape hatch in a
  payment-settlement path is exactly the kind of thing that ships by accident.
- **D5 (I4) — engineering posture resolved 2026-09-07; the product question stays with you.**
  I cannot close the "do we accept losing GrabPay and BillEase" half: it needs the RM's answer
  (A4/U5), which does not exist yet, and the trade is a commercial one. What *is* decided:
  1. **`METHODS` is derived from the confirmed enabled-channel list, never from optimism.** No
     copy is written until the RM answers in writing. Shipping a kiosk screen that promises
     BillEase to a customer standing in front of it, when Maya has not enabled it, is worse
     than shipping a shorter list.
  2. **A channel we cannot name is a channel we do not list.** If the answer is ambiguous, the
     method comes off the list until it is demonstrated working in the phase-10 pilot.
  3. **If GrabPay and BillEase are genuinely unavailable, that is a D0 input, not something to
     absorb quietly.** Removing a BNPL option can move conversion, and that belongs in the
     commercial comparison rather than being discovered after cut-over.
  **Unblocks when:** the RM answers A4/U5 (phase 1).
- **D6 (§17, I5) — ship a `PAYMENT_PROVIDER` flag, scoped narrowly, with a removal deadline**
  (resolved 2026-09-07).
  **The counter-argument I weighed:** Vercel already offers instant rollback to a previous
  deployment, so a hard cut-over plus a revert covers much of what a flag buys, at lower
  complexity. Two things decide it the other way. A Vercel rollback reverts **everything** in
  that deployment, not just payments — a coarse instrument for an incident that may be narrow.
  And **booker and vendor are two separate deployments that must flip together**; a flag flips
  them independently and in seconds, a revert needs two coordinated redeploys while real
  customers are mid-checkout.
  **Scope it tightly, or it rots:**
  - The flag gates **only the create-session provider choice** in the two routes. Nothing else
    branches on it.
  - **Both webhook handlers stay mounted for the whole overlap** — they live at different paths
    and resolve bookings by different keys, and a given booking's session belongs to exactly
    one provider, so **they cannot race** on the same `is_paid` transition. This is also the
    clean answer to I5.
  - **Removal is phase 12 and is part of the migration, not a follow-up.** A provider flag left
    in place becomes permanent dead weight and a second untested code path.
- **D7 (§15) — subscribe from day one, act on nothing: log-only for the migration**
  (resolved 2026-09-07). Acting on `PAYMENT_FAILED` / `PAYMENT_EXPIRED` / `PAYMENT_CANCELLED`
  changes the booking lifecycle and capacity holding — that is a **feature**, with UX and
  possibly schema consequences, and folding it into a provider swap would make a
  like-for-like migration impossible to verify as like-for-like.
  **But subscribe immediately anyway.** It costs one registration call each and gives us the
  evidence base — how often bookers actually abandon, how many sessions expire — that any
  future decision to release held capacity will need. Log them **structured** (event name,
  booking id, amount, timestamp), not as free text, so the follow-up plan can query the history
  rather than starting from zero. The follow-up is its own plan; do not let it grow into this
  one.
- **D8 (I6) — conditional on D0, and recorded on both plans** (resolved 2026-09-07).
  - **If D0 = migrate:** Maya through **phase 6** first, then the mobile payment-return bridge.
    The bridge is built on `vendor/app/api/kiosk/payment/create-session/route.ts` — the exact
    file this migration rewrites — so doing mobile first means building it against PayMongo and
    then rewriting it. Maya first means building it **once**, against the final shape.
  - **If D0 = do not migrate:** the mobile kiosk plan is **unblocked immediately**; nothing in
    it was ever waiting on Maya.
  Either way, the chosen order must be written onto
  `.plans/2026-09-03-vendor-mobile-kiosk-mode.md` as well — a sequencing decision recorded on

- **D9 (§6) — `redirectUrl.failure` → `?payment=failed&booking_id=…`, with neutral copy, in
  scope for the migration** (resolved 2026-09-07).
  **I reconsidered and nearly deferred this**, to stay consistent with D7's "log-only, features
  later" line: pointing `failure` at the existing `cancel` URL is zero new code. The reason
  that is wrong — **we cannot preserve today's behaviour here, because today has no failure
  redirect at all.** Under PayMongo a declined card leaves the customer sitting on PayMongo's
  page; Maya *will* send them back to us whether we handle it or not. So the choice is not
  "change vs no change", it is "a correct message vs a wrong one": reusing the cancel URL would
  tell someone whose card was declined *"Payment cancelled. Your booking is saved as pending."*
  **Copy must be neutral about cause** — the redirect says only that Maya ended the attempt, and

  completed. Your booking is saved as pending."*

## DEFERRED / COSMETIC

- **Refunds via API.** Maya offers them (180 days, partial); we have never called PayMongo's.
  Adopting them would let `bookings.status = 'refunded'` and `payout_status = 'reversed'` stop

  migration parity, and belongs in its own plan.
- **Maya Vault / saved cards.** No product requirement; would add PCI surface. Not now.
- **`booking_transactions` / `payment_reference` schema changes.** None needed. `payment_reference`

- **A `provider` column on `bookings`.** Tempting during a dual-provider overlap, but the
  `cs_`-prefix vs UUID shape of `payment_reference` already distinguishes them, and adding a
  column for a temporary state is exactly the speculative generality AGENTS.md forbids. A note in

- **CSP changes in `booker/next.config.ts`.** None. Top-level navigation is governed by neither
  `connect-src` nor `form-action`, and Maya Checkout ships no browser SDK in this design — the
  same reasoning that keeps `api.paymongo.com` deliberately absent today.
- **A Maya SDK dependency.** Rejected: the official Node SDK is a thin, lightly-maintained
  wrapper around two `fetch` calls, and adding it would trip an approval gate for no gain.
