## Launch once

Keep the **Bash terminal where you privately reloaded both test API keys** open.
Do not launch a new Bash or paste keys into chat/tool calls. Run once:

```bash
source /home/joshua/RS/.plans/scripts/run-checkout-provider-tests.bash
```

The wrapper uses only these existing variables, without asking you to paste keys:

- `checkout_test_secret`, `checkout_test_public`

They are sent through a private process pipe, not command arguments, exported
environment variables or files. No provider payload or identifying value is
printed. Core dumps are disabled for the subprocess, Node debug/preload/coverage
options are removed, and a shell flag prevents a second launch in that session.
This assumes your local machine/terminal is trusted; it cannot protect secrets
from a compromised OS, administrator, terminal instrumentation or memory reader.
JavaScript memory is not guaranteed to be securely erased.

The runner makes **at most four sequential requests** to the fixed HTTPS
PayMongo API host:

1. Create one new isolated PHP 100 test intent labelled T6-FRESH, QR Ph only.
2. Replay that creation once: exact same body and the same generated key.
3. Create one new test QR method with expiry_seconds 420.
4. Replay that creation once: exact same body and the same generated key.

Both distinct creation UUIDs are generated once and retained only in this
process's memory. Response IDs/client keys stay private, and replays compare
them locally. The intent and method are **never attached**, so no QR is generated
and no simulator/payment is initiated. T7 paid read is explicitly skipped because
the old private baseline is lost; fresh creation is not recovery of old requests.

It does not authorize payments, attach/cancel anything, change webhooks, open
URLs, list account/customer resources, contact anyone, send email or access
Supabase. Keys must be test-prefixed; all fixture modes/proof labels are checked.
Creation timestamps must be younger than **23 hours**, a conservative margin
before the provider's 24-hour key expiry. Each replay reuses its just-generated
original key; it never generates a retry key.
An unexpected duplicate resource is possible if provider idempotency fails:
the runner reports an identity mismatch and stops; it never attaches/pays it.
The existing six-intent/eight-method/eight-attach budget is not expanded. Prior
confirmed resources are 3 intents/3 methods/3 attaches. If both replays match,
the totals become 4 intents/4 methods/3 attaches. If a replay creates a duplicate
or a response is uncertain, stop and review actual/possible resource counts
before later tests; request counters are not automatically resource counts.

Only the runner's fixed JSON summary or fixed STOP message is safe to paste
back. Never dump the underlying shell variables, enable tracing/debug logs,
paste keys, save raw responses, or run the wrapper through an agent tool.

If anything stops, **do not rerun**, remove the attempt flag, restart Bash to
bypass it or manually retry requests. Report the safe summary and review the
uncertainty first. Fresh creation keys/raw responses are not persisted after
process exit, so an unknown outcome must not be retried with a new key. T7 is
explicitly skipped, not passed. Cancellation/old-capability tests remain separate; the failure simulator
case remains user-parked until later validation before staging acceptance.
